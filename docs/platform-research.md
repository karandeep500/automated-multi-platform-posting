# Platform API research

Researched on 15 November 2026 using official provider documentation. These five services expose publishing APIs; an LLM chat/completion endpoint alone would not create a public post, so none is presented as a publishing destination.

| Platform | Official documentation | Authentication / requests | Publication evidence and access |
| --- | --- | --- | --- |
| Mastodon | [Create status](https://docs.joinmastodon.org/methods/statuses/#create) | User bearer token with `write:statuses`; `POST {instance}/api/v1/statuses`, form fields `status` and `visibility=public`. Instance is configurable. | Returned `url`, `created_at`, and `visibility`; public/unlisted statuses are treated as public according to visibility metadata. Instance access policies can still restrict anonymous retrieval. |
| Bluesky | [Creating a post](https://bsky.network/docs/tutorials/creating-a-post/), [createSession](https://docs.bsky.app/docs/api/com-atproto-server-create-session), [createRecord](https://docs.bsky.app/docs/api/com-atproto-repo-create-record) | Identifier + app password to `POST /xrpc/com.atproto.server.createSession`; returned access JWT authorizes `POST /xrpc/com.atproto.repo.createRecord`, collection `app.bsky.feed.post`. | Returned AT URI provides DID and record key for a `bsky.app` permalink. Link facets use UTF-8 byte positions. The submitted `createdAt` is returned only after the provider confirms record creation. |
| DEV Community / Forem | [Create article](https://developers.forem.com/api/v1#tag/articles/operation/createArticle) | `api-key` header and `Accept: application/vnd.forem.api-v1+json`; `POST https://dev.to/api/articles` with nested `article`, `title`, `body_markdown`, and `published=true`. | Require the returned `published_at` and `url`; a draft is not reported as a success. A short message is mapped to the article body because DEV does not expose a micro-status endpoint. |
| Telegram | [sendMessage](https://core.telegram.org/bots/api#sendmessage), [Message](https://core.telegram.org/bots/api#message), [Chat](https://core.telegram.org/bots/api#chat) | Bot token in the URL; `POST https://api.telegram.org/bot{token}/sendMessage`, JSON `chat_id` and plain `text`. Bot needs posting permissions in the target channel. | Require `ok=true`, then use returned `message_id`, `date`, and `chat`. A username on a channel/supergroup provides `https://t.me/{username}/{id}`. Private channel links use `t.me/c/` and require membership; direct messages have no public link. |
| Discord | [Execute webhook](https://docs.discord.com/developers/resources/webhook#execute-webhook), [Message object](https://docs.discord.com/developers/resources/message#message-object) | Secret incoming webhook URL; `POST {webhook}?wait=true`, JSON `content` and `allowed_mentions.parse=[]`. No bot token is needed. | `wait=true` returns the created message. Server ID + returned channel/message IDs provide a permalink; returned `timestamp` is the publication time. Server/channel permissions are required, so `public_access=false`. |

## Common handling

Each adapter makes its own request and parses confirmed publication metadata. HTTP authentication/permission errors, rate limiting, rejected requests, server errors, timeouts, invalid JSON, and invalid response shapes produce independent failures. Upstream response bodies and exception strings are not reflected because they can disclose credentials. Requests do not follow redirects or automatically retry writes.

The offline contract tests validate these request formats against documented response fixtures. They do not prove that a real account has valid credentials, publishing permissions, quota, or publicly visible content. Live verification remains dependent on supplying accounts and credentials.
